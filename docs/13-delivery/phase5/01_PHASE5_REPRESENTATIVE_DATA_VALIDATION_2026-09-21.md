# 3. Fiber workbook

Primary sheet:

`FIBER`

Representative review:

- approximately 29 meaningful rows;
- summed line values: approximately EGP 1,219,600;
- all meaningful rows currently use `PC` as UOM.

Examples include:

- LEVITON / 5LLAZ-122 / Fiber Optical Cable IN/OUT ARMORED 12 CORE OM3 / qty 6283;
- LEVITON / 5LPSC-M03 / OM3 SC pigtail / qty 1937;
- LEVITON / 5LDCL-M03 / OM3 patch cord / qty 604;
- DEMA PROLINK fiber couplers/pigtails/patch cords;
- HPE / PANDUIT / COMMSCOPE items.

## Critical UOM finding

A cable line with quantity `6283` is represented as `PC`.

That is not strong enough evidence that the true operational unit is pieces.

It may represent meters or another quantity convention from the legacy sheet.

Therefore:

**Do not import legacy UOM blindly.**

Phase 5 needs a UnitOfMeasure normalization policy and import-review rule.

Candidate canonical units must be validated from real items, likely including at least:

- PC;
- M;
- ROLL;
- BOX/CARTON;

without assuming those are exhaustive.

## Critical part-number finding

Observed legacy values include:

- `NONE`;
- placeholder values;
- duplicated `14130646` for two ready-cable rows with different lengths.

Therefore:

- Part Number is searchable/master-data evidence;
- it is not a universal unique key;
- duplicate detection should produce import review context;
- HILTECH item/asset code remains the hard internal identity.

# 4. Active workbook

Primary sheet:

`SAMPLE`

Representative review:

- approximately 11 meaningful rows;
- summed line values: approximately EGP 521,100;
- all meaningful rows currently use `PC`.

Examples include:

- 3COM HP switch;
- HP-Aruba switch;
- Hikvision camera;
- SFP transceivers;
- HPE access point.

## Critical template-contamination finding

The left `DESCRPTION` field contains descriptions that clearly belong to an old UTP template while the same row's Brand / Part Number / `DESC` identify different active-network equipment.

Example pattern:

- legacy DESCRPTION resembles a cable/patch-cord row;
- Brand / Part Number identify a switch, SFP, camera or access point.

Therefore:

**legacy row columns can conflict with one another.**

Import must use staging + validation.

No production StockItem or Asset master should be created from a row until the selected canonical fields are internally coherent.

## Serialized-stock / Asset implication

The Active file contains equipment classes that may be:

- quantity-tracked StockItem before issue/install;
- serialized stock;
- individually tracked company Asset;
- client/project equipment that becomes an installed asset later.

The import contract must not classify every Active row the same way.

Classification should be explicit:

- STOCK_QUANTITY;
- STOCK_SERIALIZED;
- COMPANY_ASSET;
- future installed/client asset path where later domain ownership requires it.

Reviewed Library file:

`.xlsx(3)`

Observed fields:

- العدد;
- الرقم التسلسلي;
- سعر القطعه;
- السعر الإجمالي;

Representative review:

- 27 item rows before the total row;
- sheet total approximately EGP 49,259.5;
- quantity is present but there is no explicit UOM column;
- unit/pack semantics appear inside descriptions such as `بالعود` and `باللفه`;
- zero-quantity rows exist and must remain reviewable rather than being silently dropped;
- notes include mixed/local-source context.

## Critical legacy-column semantics finding

The column labelled `الرقم التسلسلي` is **not reliable evidence of per-unit serialization**.

Representative values include:

- `(4525/2)`;
- `(4525/6)`;
- `LOCAL`;
- `2M`;
- `مصري`.

These values behave like catalog/model/origin/pack descriptors in multiple rows, not unique Asset serial numbers.

Therefore:

- a legacy column label must never by itself select a production domain field;
- `الرقم التسلسلي` must not automatically imply `STOCK_SERIALIZED` or `COMPANY_ASSET`;
- import staging must preserve raw source columns and require explicit semantic mapping/review;
- ambiguous source-field meaning must block approval with a typed issue such as `LEGACY_COLUMN_SEMANTICS_AMBIGUOUS`;
- implicit unit words inside description require UOM review rather than parser guessing.

This strengthens the existing staging/UOM/classification decisions; it does not change the Phase-5 domain boundary or require another Slice.

# 5. Legacy stock-date / movement finding

Across UTP/FIBER/ACTIVE, columns include inbound/outbound and date-like fields.

Observed rows use values such as:

- inbound quantity populated;
- `STOCK` appearing in a date-labelled column;
- `01/04/2026` appearing in another date-labelled position;
- outbound quantity sometimes blank while remaining quantity equals opening quantity.

This is not reliable movement-event history.

Therefore the import contract must treat these sheets primarily as:

**opening inventory/master evidence as of a stated cutover date**

rather than manufacturing historical RECEIVE / ISSUE / RETURN events from ambiguous legacy columns.

Preferred migration pattern:

1. import reviewed master data;
2. create explicit opening-balance / opening-custody operation at cutover;
3. retain legacy source reference;
4. begin authoritative movement history from that cutover;
5. import older movement history only where an independently trustworthy source exists.

## Boundary conclusion

This workbook is useful evidence for:

- supplier identity/reference;
- purchase invoice reference;
- purchase chronology;
- accounting/receipt linkage candidates.

It does **not** provide item-level warehouse receiving detail in the reviewed structure.

- Phase 5 may reference invoice/purchase identifiers;

- receiving item lines require a real receipt/PO/item source or explicit manual receiving operation;
- Finance/accounting invoice truth remains separate.

# 7. Import architecture consequence

Direct one-step “Excel -> production tables” import is rejected.

Phase 5 needs an import staging/review model.

Candidate flow:

`Legacy file -> parsed staging rows -> validation issues -> human mapping/review -> approved master/opening truth`

Validation issue examples:

- UNKNOWN_UOM;
- PART_NUMBER_MISSING;
- PART_NUMBER_PLACEHOLDER;
- DUPLICATE_PART_NUMBER;
- DESCRIPTION_CONFLICT;
- BRAND_NORMALIZATION_REQUIRED;
- CATEGORY_UNMAPPED;
- SERIAL_REQUIRED_BUT_MISSING;
- QUANTITY_AMBIGUOUS;
- LEGACY_DATE_SEMANTICS_AMBIGUOUS;
- LEGACY_COLUMN_SEMANTICS_AMBIGUOUS;
- ITEM_CLASSIFICATION_REQUIRED;
- OPENING_LOCATION_REQUIRED.

The staging model must preserve:

- source filename;
- source sheet;
- source row;
- raw values;
- normalized candidate values;
- issue codes;
- review state;
- approved target master id after import.

No ambiguous row becomes authoritative silently.

# 8. Opening balance / opening custody consequence

The reviewed stock files are best modeled as cutover evidence.

For Stock:

- approved StockItem master;
- approved StorageLocation;
- approved opening on-hand quantity;
- cutover timestamp/date;
- source file/row trace.

For Asset:

- approved Asset identity;
- approved initial condition;
- approved current StorageLocation/custodian;
- optional tag creation;
- cutover operation;
- source trace.

Opening truth should be a first-class auditable migration operation, not a fake normal purchase receive if no real purchase receipt is known.

# 9. Quantity/UOM decision impact

The legacy files prove that `numeric(20,6)` is not the main unresolved question.

The real question is:

**which units and decimal rules are allowed per StockItem/category?**

Candidate policy shape:

- unit code is master/config data;
- StockItem has canonical base unit;
- quantity stored in base unit;
- display/purchase pack conversions are explicit;
- precision/rounding constrained by unit;
- movement unit must be compatible with item unit;
- no implicit conversion.

Representative validation must include:

- cable measured by length;
- discrete connectors/modules;
- packaged/carton items;
- ready-made cable assemblies;
- active devices;
- Accessories rows where UOM is implicit in Arabic description rather than a dedicated field.

# 10. Identity decision impact

Legacy evidence supports:

## StockItem hard identity

HILTECH internal `itemCode`.

Search/matching dimensions:

- Brand/Manufacturer;
- Part Number;
- normalized description;
- category;
- spec attributes.

## Asset hard identity

HILTECH internal `assetCode`.

Additional searchable attributes:

- manufacturer;
- model;
- serial;
- tag.

Serial and Part Number remain policy/search dimensions, not universal primary keys.
