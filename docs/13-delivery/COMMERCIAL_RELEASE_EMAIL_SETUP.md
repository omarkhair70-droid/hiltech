# Commercial quote export and email deployment

The released customer projection excludes private costs. The first PDF export is archived by quote version with SHA-256. The template uses embedded Plex, with rasterized A4 pages; verify real company logo, contacts and legal details before production acceptance.

Direct email uses the company SMTP account. Configure Spring Boot mail properties using deployment secrets (never commit passwords):
- SPRING_MAIL_HOST, SPRING_MAIL_PORT, SPRING_MAIL_USERNAME, SPRING_MAIL_PASSWORD
- SPRING_MAIL_PROPERTIES_MAIL_SMTP_AUTH=true (when required)
- SPRING_MAIL_PROPERTIES_MAIL_SMTP_STARTTLS_ENABLE=true and SPRING_MAIL_PROPERTIES_MAIL_SMTP_STARTTLS_REQUIRED=true (for STARTTLS providers)
- SPRING_MAIL_PROPERTIES_MAIL_SMTP_CONNECTIONTIMEOUT=10000
- SPRING_MAIL_PROPERTIES_MAIL_SMTP_TIMEOUT=10000
- SPRING_MAIL_PROPERTIES_MAIL_SMTP_WRITETIMEOUT=10000
- HILTECH_COMMERCIAL_EMAIL_FROM: verified company sender address

Verify TLS and authentication settings for the selected provider. No recipient may be sent an actual quotation without the operator confirming the address and release. SMTP_ACCEPTED means SMTP server acceptance, not inbox delivery. SENDING/UNKNOWN means verify with the provider before trying again; no blind automatic retry. WhatsApp currently uses native Android sharing, not a WhatsApp Business API.

Apply migrations in order and verify existing quote approvals, discount/tax amount reconciliation, company client isolation, PDF archive repeatability and authorized dispatch. Discount and tax are explicit monetary amounts in the quote currency, not a statutory rate calculation. Run acceptance on Windows and Android using a controlled internal recipient before enabling live sending.

## In-app SMTP connection
A release-authorized user can test/connect/disconnect SMTP in Commercial > Company & document settings. Use a provider-supported app password or SMTP credential. Server secret HILTECH_COMMERCIAL_MAIL_ENCRYPTION_KEY must be base64 of 32 cryptographically random bytes; preserve it in encrypted backup. HILTECH_COMMERCIAL_SMTP_ALLOWED_HOSTS is a trusted deployment allowlist, default smtp.gmail.com,smtp.office365.com. Only STARTTLS on port 587 is used; OAuth-only tenants need a separate OAuth integration. Existing deployment SMTP is available only if HILTECH_COMMERCIAL_LEGACY_MAIL_COMPANY explicitly maps it to the company's UUID. Disconnecting a native connection does not remove an independently configured legacy account. No secret is returned through status endpoints. Google/Microsoft OAuth and WhatsApp Business embedded signup are not implemented.

## WhatsApp Business document dispatch
Configure a company-specific connection through deployment secrets: HILTECH_COMMERCIAL_WHATSAPP_COMPANY (company UUID), HILTECH_COMMERCIAL_WHATSAPP_PHONE_ID, HILTECH_COMMERCIAL_WHATSAPP_TOKEN, HILTECH_COMMERCIAL_WHATSAPP_TEMPLATE, HILTECH_COMMERCIAL_WHATSAPP_LANGUAGE, HILTECH_COMMERCIAL_WHATSAPP_API_VERSION. The approved template must have a document header and static body (no body parameters). The operator must confirm recipient consent and number. The archived PDF is uploaded to Meta and attached to the template message. API_ACCEPTED is not delivery; provider webhooks and embedded signup are not implemented. Test only with an approved internal recipient before live use. In-app manual Meta connection is available using a phone number ID, access token, approved document template, language and Graph API version. The phone ID is verified before saving; this is not embedded signup or a live send test. Stored tokens are encrypted with the same deployment encryption key, with separate purpose binding. A separately configured deployment account remains independent of the in-app connection. OAuth account setup and Meta embedded signup remain separate tasks. The commercial backend now defaults to enabled; explicit authority and approval requirements still apply.

## Google and Microsoft OAuth
Register confidential web applications with Google (Gmail API and gmail.send plus openid/email) and Microsoft Entra (delegated User.Read, Mail.Send and offline_access). Configure HILTECH_COMMERCIAL_OAUTH_PUBLIC_BASE as the HTTPS API origin and register its exact /v1/commercial/oauth/callback URL with both providers. Supply client IDs and secrets through HILTECH_COMMERCIAL_OAUTH_GOOGLE_CLIENT_ID, HILTECH_COMMERCIAL_OAUTH_GOOGLE_CLIENT_SECRET, HILTECH_COMMERCIAL_OAUTH_MICROSOFT_CLIENT_ID and HILTECH_COMMERCIAL_OAUTH_MICROSOFT_CLIENT_SECRET. Preserve the existing encryption key. The app opens the provider browser, then the authenticated operator checks and explicitly confirms the account. Callback uses expiring single-use state and PKCE. Disable query-string logging on the callback; do not log codes or tokens. OAuth sending takes priority over SMTP. Disconnect removes the local account; revoke the grant at the provider if required. Provider registration and a controlled live send remain deployment acceptance steps.

## Meta Embedded Signup
Use the current Meta unified Embedded Signup configuration. Register the public HTTPS domain and configure HILTECH_COMMERCIAL_META_PUBLIC_BASE, HILTECH_COMMERCIAL_META_APP_ID, HILTECH_COMMERCIAL_META_APP_SECRET, HILTECH_COMMERCIAL_META_CONFIG_ID and HILTECH_COMMERCIAL_META_API_VERSION. The browser flow uses Meta's JS SDK, single-use expiring state, server-side code exchange, WABA phone membership and approved static-body document template validation, and explicit in-app confirmation. It links an existing usable number and does not register a new phone PIN, subscribe webhooks, attach a credit line, or claim provider approval. These steps depend on the actual Meta business and partner model. Require a controlled live send, and complete provider registration/App Review before exposing this to production. Avoid logging provider codes/secrets.

## WhatsApp status webhooks
Configure a separate random HILTECH_COMMERCIAL_META_WEBHOOK_VERIFY_TOKEN and register the public HTTPS /v1/commercial/meta/webhook callback. Subscribe the Meta app to the messages webhook field and the company WABA. The receiver verifies the raw-body HMAC-SHA256 signature with the Meta app secret before updating an exact originating phone, recipient and provider message or echoed operation ID. Signed sent/delivered/read/failed status is separate from HTTP acceptance. Repeated and out-of-order statuses do not regress delivered/read states. No historical inbound message bodies are retained. Existing attempts without a sender phone ID cannot be reconciled by this receiver. Verify with a controlled real message. Meta app review, phone registration and WABA subscriptions still require actual provider access.
